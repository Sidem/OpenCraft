# OpenCraft

**A voxel sandbox with a factory builder inside it, in the browser.** You mine and build in a Minecraft-like world,
then automate the mining with miners, belts, smelters and power lines, Satisfactory-style. The whole game is written by
AI coding agents, and the repository is set up so that a cold-started agent can ship a feature quickly.

**Play it: <https://sidem.github.io/OpenCraft/>** (desktop browser, keyboard and mouse). No install, no account.

- **Engine:** Rust compiled to WebAssembly (SIMD128), driving raw WebGL2 through a thin TypeScript host. No game engine,
  no runtime dependencies beyond three small Rust crates (npm holds only build tools).
- **No asset files:** every texture and sound effect is generated by code at startup.
- **Deterministic core:** a fixed 60 Hz simulation that changes only through queued actions. It powers saves, tests
  and lockstep co-op.
- **Size:** about 66k lines of Rust (20k of them tests, 830+ tests) and 12k lines of TypeScript.

## What sets the game apart

- **Factories in a voxel world you can reshape.** Machines, belts, lifts, pipes and rails sit in the same block world
  you dig. Quarries leave real pits, and a terraforming planner with drones flattens, fills or tunnels whole sites.
- **Finite deposits with shared pools.** Ore comes in outcrops, veins and lodes. Each holds a pool of units shared by
  all its blocks, with a draw limit and real depletion. Hand mining is lossy. Machines are efficient, so automating
  is how you progress, not a chore.
- **A long, data-driven tech tree.** It starts with stone tools and hand smelting. It runs through steel, steam,
  electronics, trains, oil, nuclear power and AI datacenters, and is heading for rockets and orbit. Research labs and
  science packs gate it, and machine tiers Mk1–Mk5 upgrade in place with kits.
- **Peaceful and open-ended.** No combat and no fail state. Worlds have biomes, a day/night cycle, block lighting,
  water, prospecting tools and a world map.
- **Co-op for 2–4 players.** Player-hosted over WebRTC with deterministic lockstep: only actions travel, and machines
  compare state hashes every second.
- **A first minute that hooks.** A new world opens in front of a broken production line with a missing belt. Fixing it
  teaches the controls and starts the player's first factory.
- **Built-in sound designer** (key O): every material's procedural sound is tunable with plain-language dials.

The player's manual is in [docs/PLAYING.md](docs/PLAYING.md) (controls, worlds, co-op, crafting) and
[docs/FACTORY.md](docs/FACTORY.md) (deposits, machines, power, research and every later era).

## Quick start

Prerequisites: Rust stable (`rust-toolchain.toml` pins it and adds the `wasm32-unknown-unknown` target),
[`wasm-pack`](https://rustwasm.github.io/wasm-pack/) (`cargo install wasm-pack`) and Node.js 20.19 or newer.

```bash
npm install
npm run dev
```

Open <http://localhost:5173>. `?seed=1234` starts a new world with that seed, and `?rd=12` sets the render distance in
chunks (2–24, default 8).

| Command             | What it does                                                                         |
| ------------------- | ------------------------------------------------------------------------------------ |
| `npm run dev`       | Vite plus a Rust watcher: any `.rs` change rebuilds the wasm and reloads the page    |
| `npm run check`     | The one gate before a commit: format, clippy, tests, typecheck, size budgets (quiet) |
| `npm test`          | Engine tests only (`cargo test --workspace`; add `-q <name>` to filter)              |
| `npm run build`     | Production build into `dist/` (wasm, typecheck, bundle)                              |
| `npm run build:wasm`| The engine only; run once before `npm run check` so the TS bindings exist            |

## Built for fast iteration by AI agents

Every session starts cold, so the codebase is designed around one cost: how much an agent must read before it can make
a correct change. Keeping that small matters as much as any feature.

### A short, fixed reading path

1. [CLAUDE.md](CLAUDE.md) (under 60 lines): the rules that matter and where everything else lives.
2. [docs/DEV_PLAN.md](docs/DEV_PLAN.md): a status line, the decisions that bind new work, the rules, and the
   next steps with their acceptance criteria. Only current work is detailed. Later work lives in
   [docs/ROADMAP.md](docs/ROADMAP.md), every settled decision in [docs/DECISIONS.md](docs/DECISIONS.md) and finished
   work in `docs/history/`.
3. [docs/CODEMAP.md](docs/CODEMAP.md): an index, one line per module; [docs/EXTENDING.md](docs/EXTENDING.md) has the
   recipes for adding blocks, items, recipes, machines, API methods, UI panels and sounds.
4. The area's conventions: [crates/engine/CLAUDE.md](crates/engine/CLAUDE.md) or [web/src/CLAUDE.md](web/src/CLAUDE.md).

Then read only the module you touch. Each one opens with a header saying what it owns, its invariants and how to
extend it. To see the engine's API from TypeScript, read the generated `web/src/wasm/engine.d.ts`, not the Rust source.

### Small files, local changes, content as data

- **Size budgets, enforced by `npm run check`:** source files warn at 400 lines and fail at 600 (tests excluded), docs at
  300/500, `CLAUDE.md` files at 60/100. An oversized file is split before anything is added to it.
- **One feature is one module or folder**, plus at most one registration line. There are no god objects.
- **Content is data.** Blocks, items, recipes, machines and techs are table rows. Every machine follows the same content
  architecture ([docs/TECH_TREE.md](docs/TECH_TREE.md) section 8), and each era's recipes are listed in
  [docs/TECH_ERAS.md](docs/TECH_ERAS.md).
- **Tests live beside their module** in `src/<module>/tests.rs`, never inline, so source files stay short to read.
- **Boring, explicit code.** No speculative abstractions: a registry appears when the second instance does.

### Fast, trustworthy feedback without a browser

- **Headless scenario tests** drive the full `Game` the way a player would: stream a world, place a miner, belts and a
  box, run ticks, assert on inventories. Co-op is tested by wiring a host and a client through bytes. These replace
  most manual play-testing.
- **Determinism makes failures reproducible.** Worlds are seeded, the core runs on fixed ticks, and its state hashes.
  A golden hash catches unintended changes to saved state, and a test checks that results never depend on frame rate.
- **One quiet command.** `npm run check` prints one line per step and shows details only for failures, so an agent's
  context isn't flooded. CI runs the same checks on every push.

### A scriptable game for visual checks

When a change has to be seen, the running game is `window.opencraft.game` in the console or an agent's browser pane.
`run_ticks(n)`, `skip_time(s)`, `give(id, n)`, `teleport(x, y, z)`, `find_deposit(tier)`, `block_at(x, y, z)` and
`state_hash()` set up any scene in one script, with no pointer lock needed. `.claude/launch.json` lets parallel
sessions each run their own dev server. [docs/WORKFLOW.md](docs/WORKFLOW.md) has the exact recipes and the Windows
gotchas.

### Parallel work without collisions

Art (textures and models) is improved on the `art` branch while features land on `main`.
[docs/ART_HANDOVER.md](docs/ART_HANDOVER.md) says which files each side owns. Because the assets are code, there is no
binary asset pipeline to merge.

## Architecture

```
┌──────────────────────── Rust → wasm (crates/engine) ─────────────────────────┐
│ Game (lib.rs, api/): what the host calls; acts for the local player          │
│  ├─ core: Sim        deterministic: tick, world edits, factory, deposits,    │
│  │                   inventories, rng. Changes only by applying Actions at   │
│  │                   a tick, and reports back with SimEvents                 │
│  ├─ authority        every player's body (physics), loose items, pickups     │
│  └─ view (local)     camera, targeting, mining, streaming, greedy meshing,   │
│                      box instances, sounds, toasts                           │
│ save.rs: the core's bytes (also its state hash) + bodies + items ⇄ save file │
└───────────────▲──────────────────────────────────────────────┬───────────────┘
      input, dt │                                              │ pointers into wasm memory
┌───────────────┴───────── TypeScript platform (web/src) ──────▼───────────────┐
│ input.ts · render/ (WebGL2) · ui/ (DOM) · audio/ · save/ (IndexedDB) · net/  │
└──────────────────────────────────────────────────────────────────────────────┘
```

Rust owns all game state and every hot loop. TypeScript forwards input, uploads data to the GPU, draws the HUD and
stores saves; it keeps no game state. Meshes, instances and sound events are read as typed-array views straight from
wasm memory, with no copy and no serialization. Co-op runs the same core on every machine: the host orders actions
into per-tick frames, and a client whose state hash differs resyncs from a snapshot.

Performance choices worth knowing before touching the renderer or the world:

- 32³ chunks, 256 blocks tall; uniform chunks take no heap memory.
- Greedy meshing with per-vertex AO and smooth light, which is computed while meshing and never stored.
- 5 bytes per vertex, a texture array instead of an atlas, separate opaque and cutout passes, camera-relative
  rendering, and all box instances (items, belts, machine parts) in one instanced draw call.
- Order-independent world generation, so chunks can generate in any order.
- Lazy factory state: links are rebuilt only on edits, and deposit pools are tracked only once touched.
- Release builds use SIMD128, fat LTO and `wasm-opt -O3`.

## Repository layout

| Path | What it is |
| ---- | ---------- |
| `crates/engine/` | The Rust engine: all game state, simulation, world generation, meshing, audio synthesis |
| `web/` | The TypeScript host: `web/src` (render, input, UI, audio, saves, co-op networking), `index.html` |
| `signal/` | A Cloudflare Worker that introduces co-op peers for WebRTC; no game data passes through it |
| `scripts/` | Build, dev watcher, `check`, size budgets and wasm-size tools |
| `docs/` | The plan, code map, roadmap, tech tree, workflow and the player's manual |

## Deployment

Every push to `main` runs `.github/workflows/pages.yml`, which builds the wasm, runs `npm run check`, bundles with Vite
and publishes `dist/` to GitHub Pages. **Pushing to `main` deploys the live site.**
