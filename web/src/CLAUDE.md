# Web host conventions (web/src)

TypeScript + WebGL2 + DOM + Web Audio: a thin platform layer. Module map: `docs/CODEMAP.md`.

## Rules

- **No game state in TS.** Read everything from `game` (the wasm `Game`) each frame; send input and
  actions to it. Mutating calls (`click_slot`, `craft`, `select_slot`, `drop_selected`, `give`…) are
  engine actions applied at the next tick, so read results on a later frame (`inventory_version`), not
  right after the call. If TS needs a number the engine owns, expose a getter (see `api/content.rs`) rather than
  copying the constant. Existing mirrors to remove when touched: `INSTANCE_FLOATS` (`render/boxes.ts`),
  the 6 floats per sound event (`main.ts`), `MATERIALS` and `EVENT_ACTIONS` order (`audio/`).
- **Zero-copy bulk data.** Meshes, instances, sounds and textures are typed-array views on
  `wasm.memory.buffer`. Use a view immediately and never keep it: it becomes invalid when wasm memory
  grows.
- **One UI component, one file pair:** `ui/<name>.ts` plus `ui/<name>.css`, imported at the top of that
  TS file. Shared styles (`.hidden`, `.secondary-btn`, `.close-btn`, theme variables) live in `base.css`.
  Build DOM with `h()` / `button()` from `ui/dom.ts`.
- **One `game` per page.** Switching worlds saves and reloads the page (`save/session.ts`), so panels
  take `game` once in their constructor. Save bytes are the engine's (`game.save()`, `Game.load`); TS
  only stores them.
- Every file starts with a header comment: what it owns and how to extend it.
- Size budgets: 400/600 lines per TS file, 300/500 per CSS file (`npm run check` reports them).

## API and bindings

- `web/src/wasm/` is generated by `npm run build:wasm` (gitignored). `engine.d.ts` lists every engine
  method; read it instead of the Rust source when you only need the API.
- A Rust change needs `npm run build:wasm` (or the running `npm run dev`) before TS sees it.
- `npm run typecheck` (or `npm run check`) needs those bindings to exist.

## Verifying in the browser

Prefer engine tests; use the browser for visual proof (`docs/WORKFLOW.md` section 2 has the details).

- `preview_start` name `opencraft`, then drive `window.opencraft.game` with `javascript_tool`.
  `window.opencraft` also exposes `renderer`, `sound`, `soundLab`, `inventory`, `machine` (panel: `open(x, y, z)`)
  and `session`. The frame loop opens panels from `game.take_panel_request()`; while rAF is paused, do it by hand.
- Pointer lock never engages in the automated pane, and `requestAnimationFrame` pauses while the pane is
  hidden: step the engine by calling `game.update(1/60)` yourself.
- Hide the menu: `document.getElementById('menu').classList.add('hidden')`. A screenshot forces a render.
- Inventory screen DOM order is backpack first: find hotbar slot `i` by its `.key` label (`i + 1`).

## Style

- Match the surrounding code: 2-space indent, single quotes, semicolons, lines up to about 120 chars.
- Plain classes and functions; no framework, no runtime dependencies (only `vite` and `typescript`).
- User-facing text is plain language; the player is not assumed to know the jargon.
